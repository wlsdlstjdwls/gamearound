## 사양 축 3단계 — 왜 설계와 다르게 만들었나

설계(`docs/기획_사양_내PC호환성_2026-09-17.md` §6)는 `(기기, 게임)` 판정 캐시를 그렸다. **안 그렇게 했다.**

그 표는 사용자 수만큼 커진다(기기 10대 × 본편 14,715). 정작 목록 필터에 필요한 것은 기기마다 다른
답이 아니라 **게임마다 하나뿐인 요구선**이다. 기기 쪽 값(티어 셋)은 질의 시점에 사전에서 뽑으면 되고,
그러면 무효화도 사용자와 무관해진다 — 사양이나 사전이 바뀐 게임만 다시 접는다.

접는 규칙은 새로 쓰지 않고 `lib/hardware/verdict` 의 `requiredTier` 를 그대로 부른다.
규칙이 두 벌이 되면 목록과 상세가 같은 게임에 다른 답을 한다.

**기기는 주소에 티어로 실린다**(`?rig=w.9.10.16` = OS, CPU티어, GPU티어, 메모리GB).
기기 id 를 실으면 비회원 기기는 서버가 되찾을 길이 없고(브라우저에만 있다) 목록 캐시가 사람 수만큼
쪼개진다. 티어로 실으면 같은 급의 컴퓨터를 쓰는 사람들이 한 캐시를 나눠 쓴다.

실측(본편 13,045 중 문턱 있는 것 3,496):

| 기기 | 남는 게임 |
|---|---|
| 낡은 노트북 (i3-4130 / HD 4600 / 8GB) | 1,468 |
| 보급형 (i5-8400 / GTX 1060 / 16GB) | 3,163 |
| 요즘 본체 (7800X3D / RTX 4070 / 32GB) | 3,424 |

문턱 줄의 판정 가능 비율: windows 2,515 / 3,498 (72%), mac 208 / 959, linux 247 / 566.

## 매장 축 2단계

신청서를 **별도 표로 두지 않았다** — 신청서가 곧 매장이다(`status='pending'`). 표를 나누면 승인할 때
값을 한 벌 옮겨 적어야 하고 그 순간 두 표가 어긋날 자리가 생긴다. 반려도 행을 지우지 않고 사유를
남긴 채 pending 으로 되돌린다. **"pending 인데 사유가 있다" 가 곧 반려**고, 고쳐서 다시 낼 자리가 그 행이다.

승인은 세 곳을 한 번에 바꾼다(매장 상태, 대표 계정 역할, 직원 표의 owner 행). neon-http 는 대화형
트랜잭션이 없지만 `db.batch` 가 한 트랜잭션으로 간다 — 실측으로 확인했다(active + owner + seller 가 함께 선다).

**감사 컬럼을 실제로 채우는 첫 쓰기 경로다.** 관리자가 한 일은 `updated_source='admin'` 으로 남는다.

안 한 것: 증빙 업로드(저장소가 없다), `/shops` 매장 찾기와 `/shops/[slug]` 매장 페이지(3단계 몫).
그래서 승인된 매장주에게 보여 줄 링크가 아직 없다 — 상태 화면이 "승인됐어요" 까지만 말한다.

## 데이터 수정 (되돌릴 근거)

- **예약 특전 4건** — `games.content_type` 을 `game` 에서 `dlc` 로. 제목으로 찾을 수 있다
  (`title_en` 에 pre-order + bonus/pack). 지운 행은 없다.
- **DLC 병합 79건** — 진 행의 `game_platforms`, `game_source_refs`, `game_genres`,
  `game_companies`, `playtimes` 를 이긴 행으로 옮기고 진 행을 지웠다. **백업 테이블은 만들지 않았다** —
  옮긴 자식 행은 그대로 살아 있고 지워진 것은 게임 껍데기뿐이다(가격 스냅샷 앞뒤 20,875 → 20,876, 손실 0).
- **문턱 5,023줄** — 언제든 `pnpm floors:backfill` 로 다시 접힌다(스토어에 묻지 않는다).
