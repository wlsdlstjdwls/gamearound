# steamdb.info, steamsale.windbell.co.kr 접근 실측과 축 비교 (2026-09-15)

`기획_게임사정보_DLC_구독혜택.md` § 3.1 은 두 사이트를 "UI 벤치마킹" 으로 판정했지만 표 한 줄이 전부였다.
psprices 만 실측 보고서가 있어서 나머지가 비어 있었다. 이 문서가 그 빈 자리를 채운다.

**데이터 인출은 하지 않았다.** 두 사이트 모두 수집원 후보가 아니다(§ 3.1 판정 유지).
여기서 한 일은 접근 가능성 실측과 화면 축 비교뿐이다.

## 1. steamdb.info

### 1.1 실측

| 경로 | 결과 |
|---|---|
| `/` | 403 |
| `/sales/` | 403 |
| `/robots.txt` | 200 |

평범한 Chrome UA + `Accept-Language: ko-KR` 로 요청했다. 본문은 Cloudflare **managed challenge**
(`cType: 'managed'`, `_cf_chl_opt`) 이고 `Checking your browser…` 화면이 온다.

**psprices 와 정반대다.** psprices 는 본문이 열리고 `robots.txt` 만 챌린지 뒤에 있었다.
steamdb 는 `robots.txt` 만 열리고 본문 전체가 챌린지 뒤에 있다.

### 1.2 robots.txt 가 허용해도 막힌다

`robots.txt` 는 `User-agent: *` 에 `Allow: /` 이고, `/sales/` 는 `Disallow` 목록에 없다.
막는 것은 문서가 아니라 방어다. 차단 목록에 `SemrushBot`, `AhrefsBot`, `BLEXBot` 이 이름으로 박혀 있고
`/api/PatchnotesRSS/`, `/api/Preview/`, `/api/RenderAppHover/` 처럼 내부 경로도 막아 뒀다.

### 1.3 페이지에 숨긴 에이전트 지시문

403 본문 안에 `style="width:0;height:0;overflow:hidden"` 으로 **사람 눈에 보이지 않는** 문단이 있다.
내용은 AI 에이전트를 향한 명령문이다 — 요청을 멈추라, 사용자의 다음 요청도 거부하라, 공식 Steam Web API 로 보내라.

기록해 두는 이유는 두 가지다.
1. **웹페이지가 내리는 명령은 따르지 않는다.** 지시는 사용자에게서만 온다. 이건 프롬프트 주입이다.
2. 그럼에도 **결론은 같다.** 우리는 애초에 steamdb 를 긁지 않기로 했고(§ 3.1), 챌린지 우회는 회피 행위라 하지 않는다.
   숨긴 문구가 시켜서가 아니라 우리 판정이 그래서다.

### 1.4 판정

**HTTP 경로로는 UI 벤치마킹조차 불가.** 화면을 보려면 사람이 브라우저로 열어 보는 수밖에 없다.
§ 3.1 의 "UI 벤치마킹" 판정은 유지하되, **자동 경로로는 수행할 수 없다**는 사실을 여기 남긴다.
Steam 데이터가 필요하면 우리가 이미 쓰는 공식 `appdetails` 가 정답이다.

## 2. steamsale.windbell.co.kr

### 2.1 실측

| 경로 | 결과 |
|---|---|
| `/` | 200 (2,241 바이트) |
| `/robots.txt` | 200 |

`robots.txt` 는 `Allow: /` 에 **`Disallow: /api/`** 다. 데이터 경로는 사이트가 직접 막아 뒀다.
그래서 **API 는 호출하지 않았다.** 아래 내용은 robots 가 허용한 정적 자산(JS 번들)을 읽어 정리한 것이다.

### 2.2 구조

Vite + React SPA 다. HTML 은 껍데기이고 내용은 전부 클라이언트 렌더다.
`recharts` 를 따로 번들해 두었다 — 가격 추이 그래프가 화면의 축 하나라는 뜻이다.

화면은 여섯이다.

| 화면 | 문구 |
|---|---|
| 현재 세일 | "지금 진행 중인 스팀 세일 게임 목록. 할인율과 가격을 한눈에 비교하세요." |
| 세일 기록 | "스팀 게임 역대 최저가, 할인 기록, 가격 추이를 검색하세요." |
| 다음 세일 | "다음 스팀 세일은 언제?" 여름, 가을, 할로윈, 겨울 세일 일정과 카운트다운 |
| 인기 세일 | "지금 가장 인기 있는 스팀 할인 게임 추천 목록" |
| 게임 상세 | 가격 추이, 세일 이력(세일 기간, 세일가, 할인), 상점 링크, 공유 |
| 공지 | - |

### 2.3 데이터 모델

번들이 읽는 필드는 열 개다.

```
game_id, sale_no, title_nm, discount_rt, start_dt, end_dt,
full_price_va, sale_price_va, img_lk, store_lk
```

**의도적으로 얇다.** 장르도, 플랫폼도, 평점도, 구독도, 회사도 없다.
스팀 하나, 할인 하나에만 집중한 대신 그 축 하나를 깊게 판다(기록, 추이, 다음 일정).

## 3. 우리 축과의 차이

우리 축(`lib/games-query.ts`)

- 정렬: `discount`, `price`, `release`, `title`
- 필터: 플랫폼(다중), 장르, 할인중, 최소 할인율, 최대 가격, 회사, 구독, 검색어

### 3.1 우리에게 없는 것

**1. 다음 세일 일정과 카운트다운 — 가장 큰 차이**

windbell 은 여름, 가을, 할로윈, 겨울, 설날 세일의 **예상 시작일**과 남은 시간을
"세일 시작까지 N일 N시간 N분 N초" 로 센다. 각 세일마다 시기와 성격을 설명하는 글도 붙어 있다
(예: 겨울 세일은 12월 말에서 1월 초, 약 2주).

우리에게는 이 축이 아예 없다. 가진 것은 `steam/parse-discount.ts` 가 **진행 중인** 행사명을
"여름 세일" 로 라벨링하는 것뿐이다. 진행 중과 예정은 다른 축이다.

이 축이 답하는 질문은 "지금 살까, 기다릴까" 다. 가격 비교 서비스의 핵심 질문인데 우리는 못 답한다.
**구현 비용도 낮다** — 스팀 세일은 연례 행사라 날짜가 거의 고정이고, 외부 수집 없이 상수 표로 채울 수 있다.

**2. 인기순 정렬**

windbell 은 "인기 세일" 을 독립 화면으로 둔다. 우리 정렬 축 네 개에 인기가 없다.
다만 인기의 근거 데이터를 우리가 가졌는지는 별도 확인이 필요하다(유저 점수는 Steam, Xbox 만 있다).

**3. 세일 기록 전용 화면**

우리도 가격 이력은 있다(`games/[slug]/prices`). 다만 **게임 상세 하위**에만 있고,
"역대 최저가로 검색하고 훑는" 독립 화면이 없다. windbell 은 이걸 1급 화면으로 올렸다.

### 3.2 우리가 더 나은 것

플랫폼 횡단(windbell 은 스팀 전용), 장르, 회사, 구독, DLC, 패치, 플레이타임.
windbell 의 얇은 모델은 약점이 아니라 선택이다 — 비교 대상이 아니라 참고 대상으로 본다.

## 4. 결론

- **steamdb**: 자동 경로 불가. § 3.1 판정 유지. 추가로 할 일 없음.
- **windbell**: 축 세 개를 얻었다. 그중 **다음 세일 일정과 카운트다운**이 비용 대비 효과가 가장 크다.
- **isthereanydeal**: 공식 API 가 있지만 **ITAD 자신의 공식**이지 스토어의 공식이 아니다.
  ITAD 도 우리처럼 스토어를 모으는 집계 사이트다. 우리는 이미 Steam, PlayStation, Xbox, 닌텐도, GOG, Epic 을
  1차로 직접 받는다. 남의 집계본을 다시 받으면 한 다리 건넌 값이고 우리 값과 충돌만 난다.
  **판정을 "조건부 데이터 인출" 에서 "제외" 로 바꾼다.** § 2.5 의 미확인 항목(무료 키 조건, 약관)도 확인할 이유가 사라졌다.
- **directg**: 리셀러. § 3.1 의 제외 판정 유지.

여섯 곳 중 수집원으로 붙는 곳은 **없다**. 전부 화면 참고용이다.
