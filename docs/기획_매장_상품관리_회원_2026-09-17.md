# 매장 상품관리, 판매, 회원 — 설계서 v3 (2026-09-17)

기획서 v2 §5 "판매업체", 확장2 "매장 재고 연동, 중고거래" 를 구조로 내린 문서.

**v3 에서 바뀐 것**
- 테이블 이름 규칙을 세우고 전부 다시 지었다(§1). 접두를 `shop_` 으로 쓴다 — 이유는 아래
- `sellers` 층을 없앴다. **개인 판매자도 매장으로 본다**(§3)
- 상품이 어느 매장에서 등록됐는지 컬럼으로 드러낸다(§4)

---

## 0. 세 줄

1. **게임(정보)과 상품(판매물)은 다른 테이블이다.** 게임은 크롤러가 쓰고, 상품은 사람이 쓴다. 둘은 매핑으로 잇는다.
2. 파는 주체는 전부 **매장**이다. 사업자 매장이든 개인이든 같은 표에 산다.
3. 지금 만드는 것은 **A(안내)** 다. B(예약), C(결제, 배송)는 테이블을 더하는 일이지 뒤집는 일이 아니게 설계한다(§12).

---

## 1. 이름 규칙

### 왜 `store_` 가 아니라 `shop_` 인가

**이 레포에서 `store` 는 이미 "디지털 스토어" 다.** 어댑터 계층 전체가 그 뜻으로 쓴다.

- `StoreSnapshot` — 스팀, PS, Xbox 에서 긁어 온 가격과 메타
- `storeUrl` — 스팀 상품 페이지 주소

여기에 `store_listings`(매장 판매 목록)를 더하면 **같은 낱말이 두 뜻으로 산다.**
코드를 읽는 사람이 매번 "이 store 는 어느 쪽이지" 를 되묻는다.

그래서 오프라인 매장은 **`shop`** 으로 못 박는다. 화면 문구는 둘 다 한국어라 문제가 없다
(디지털은 "스토어", 오프라인은 "매장").

### 규칙 여섯

1. **접두는 소유자다.** 그 행이 누구 것인지로 시작한다 — `shop_`, `product_`, `order_`, `game_`, `user_`
2. 복수형을 쓴다 — `shops`, `products`
3. **사전(이름표) 성격은 `_models` 로 끝낸다** — `hardware_models`, `gpu_models`, `cpu_models`
4. **이력은 `_events`, 실행 기록은 `_logs`** — `shop_stock_events`, `shop_sync_logs`
5. 잇는 표는 `주체_대상` — 기존 `game_companies`, `game_platforms` 와 같은 결
6. **약어를 새로 만들지 않는다.** 업계 표준어(SKU, DLC, GPU, CPU)만 허용

### 이름표 (v2 대비)

| v2 | v3 | 왜 |
|---|---|---|
| `sellers` | 없앰 | 개인 판매자도 매장으로 본다(§3) |
| `stores` | `shops` | 디지털 스토어와 낱말이 겹친다 |
| `store_members` | `shop_staff` | "members" 는 고객 회원으로 읽힌다. 이건 직원이다 |
| `store_invites` | `shop_staff_invites` | 무엇에 대한 초대인지 이름에 있어야 한다 |
| `sales_channels` | `shop_channels` | 매장 소속이 드러나야 한다 |
| `product_skus` | `products` | SKU 는 상품의 다른 말일 뿐이다. 층 이름이 둘일 이유가 없다 |
| `sku_components` | `product_components` | 위와 짝 |
| `listings` | `shop_listings` | 누구의 판매 등록인지 이름만 봐도 알아야 한다 |
| `listing_units` | `shop_listing_units` | 같은 이유 |
| `listing_photos` | `shop_listing_photos` | 같은 이유 |
| `stock_events` | `shop_stock_events` | 누구 재고인지 |
| `store_integrations` | `shop_integrations` | 접두 통일 |
| `store_sync_runs` | `shop_sync_logs` | 기존 `sync_logs` 와 짝을 맞춘다 |
| `hardware_platforms` | `hardware_models` | `platformEnum` 과 헷갈린다. 사전은 `_models` 규칙 |

라우트도 같이 맞춘다: `/stores/*` 대신 **`/shops/*`**. 관리자는 `/shops/admin`(§11).

### 딸린 제안 (지금 안 해도 됨)

지금 `platformEnum` 의 값은 `steam, ps5, ps4, xbox, switch, switch2, epic, gog` 인데
**steam, epic, gog 는 플랫폼이 아니라 스토어다.** 이름이 실제와 어긋나 있다.
언젠가 `storeEnum` 으로 고치면 `hardware_models`(진짜 기종)와 뜻이 깨끗하게 갈린다.
지금 하면 마이그레이션이 크니 기록만 남긴다.

## 2. 공통 컬럼 — 모든 테이블

**예외 없이 감사 컬럼을 갖는다.**

```
created_by   uuid null       created_source  text
updated_by   uuid null       updated_source  text
created_at   timestamptz     updated_at      timestamptz
```

- `schema.ts` 에 `auditColumns()` 헬퍼를 두고 모든 테이블이 펼쳐 쓴다
- **행위자가 사람만이 아니다.** 이 레포는 쓰기의 대부분을 크롤러가 한다.
  `created_by` 가 users FK 하나면 크롤러 행을 못 적는다. 그래서 `*_source` 를 같이 둔다
  (`crawler:steam`, `cron:crawl`, `admin`, `shop:{id}`, `integration:naver`)
- **기존 테이블도 소급한다.** 마이그레이션 + 백필, 과거 행은 `system`
- `updated_at` 을 DB 트리거로 걸지 않는다. sync 의 "값이 실제로 달라질 때만 UPDATE" 규칙(AGENTS §7)과 부딪쳐
  안 바뀐 행의 시각이 매 실행 움직인다. 쓰기 경로에서 채운다

## 3. 매장 — 개인 판매자도 매장이다 (v3 결정)

v2 는 `sellers`(판매 자격)와 `stores`(매장 정보)를 갈랐다. **되돌린다.**

층을 하나 없애서 얻는 것:
- 조인이 하나 준다. `shop_listings` 가 바로 `shops` 를 본다
- 이름이 직관적이다. "판매자" 와 "매장" 이 따로 있으면 어느 쪽에 무엇이 있는지 매번 헷갈린다
- 평판, 정지, 정산이 어차피 같은 규칙이다. 표를 나눌 이유가 없었다

층을 없애도 잃지 않는 것: **개인 판매자 구분은 컬럼 하나로 된다.**

### shops

| 컬럼 | 뜻 |
|---|---|
| `shopType` | `business`(사업자 매장) / `personal`(개인 판매자, 중고거래) |
| `slug`, `name` | 공개 주소와 표시 이름 |
| `ownerUserId` | 대표 계정. 실제 권한은 `shop_staff` 가 정한다 |
| `bizRegNo` | 사업자번호. `personal` 이면 null |
| `addressType` | `offline`(실제 매장) / `online_only` / `none`(개인) |
| `address`, `lat`, `lng` | 오프라인 매장만 필수 |
| `phone`, `hours`, `description` | 매장 정보 |
| `status` | `pending` / `active` / `suspended` |
| `suspendReason`, `approvedAt`, `approvedBy` | 심사 흔적 |
| `ratingAvg`, `ratingCount` | 평판 |

중고거래를 켜는 날 하는 일은 **`shopType = 'personal'` 행을 허용하는 것뿐이다.**
심사 기준과 필수 항목만 갈리고, 주문도 정산도 평판도 같은 길을 탄다.

### shop_channels — 판매 채널 (온라인 확장)

`shopId`, `channel`(`offline` / `naver_smartstore` / `coupang` / `own_mall`), `externalShopId`, `url`, `isActive`.

지금은 `offline` 행 하나뿐이다. **매장 하나가 여러 채널을 가질 수 있다** —
오프라인 매장이 스마트스토어도 함께 하는 경우가 흔하다. 재고 연동(§8)도 채널 단위로 걸린다.

## 4. 상품 — 실물 게임의 형태를 담는다

### 층 구조

```
games               무슨 게임인가            크롤러 소유   기존 테이블
  |  (매핑, §5)
products            무엇을 파는 물건인가      사람 소유     신규
  |
shop_listings       누가 얼마에 몇 개 파는가  매장 소유     신규
  |
shop_listing_units  그 중 이 한 점            매장 소유     신규 (중고, 레트로)
```

갈라야 하는 이유: 같은 게임이 스탠다드, 디럭스, GOTY, 한정판으로 나오고, 같은 에디션도 곽팩과 무곽이 다른 물건이며,
포켓몬 세트는 게임 둘을 가리키는 상품 하나고, 중고는 한 점 한 점 상태가 다르고,
굿즈와 하드웨어는 게임이 아예 없다.

### products — 상품 정의 (매장끼리 공유한다)

| 컬럼 | 뜻 |
|---|---|
| `barcode` | EAN, JAN, UPC. **실물 상품의 자연키다.** 이게 있어야 매장 둘이 같은 물건을 같은 상품으로 만난다 |
| `gameId` | 대표 게임. 세트면 대표 하나, 굿즈면 null |
| `hardwareCode` | `hardware_models` 참조. `platformEnum` 을 쓰지 않는다(§6) |
| `regionCode` | `KR`, `NTSC-J`, `NTSC-U`, `PAL`. 레트로는 안 맞으면 기기에서 안 돌아간다 |
| `editionName` | 스탠다드, 디럭스, GOTY, 한정판, 초회한정 |
| `packageType` | `cart_only`(무곽) / `boxed`(곽팩) / `big_box` / `digipak` / `code_card` / `set` |
| `languageKo` | 한글판 여부. 국내 중고 시세를 가르는 값이다 |
| `releaseYear`, `publisherLabel` | 발매 연도, 국내 유통사 |
| `isOfficial` | 정품 여부. 레트로에는 복각과 비정품이 섞인다 |
| **`registeredShopId`** | **이 상품을 처음 만든 매장**(§4.1) |
| `verifiedAt`, `verifiedBy` | 관리자가 확인한 상품인가 |

### 4.1 "이 상품을 어느 매장이 등록했나" — 볼 수 있다

두 경로로 답한다. 둘 다 둔다.

- **`registeredShopId`** — 최초 등록 매장. 조회와 필터에 쓴다.
  감사 컬럼의 `created_source = 'shop:{id}'` 로도 알 수 있지만, 그건 텍스트라 조인과 인덱스가 안 된다.
  "이 매장이 만든 상품 목록", "등록이 몰리는 매장" 같은 질문에는 **컬럼이 있어야 답한다**
- **감사 컬럼** — 누가(사람), 언제, 그 뒤로 누가 고쳤나

같이 봐야 하는 값 하나 더: **이 상품을 파는 매장이 몇 곳인가**는 `shop_listings` 를 세면 나온다.
등록 매장이 한 곳이고 파는 곳도 한 곳이면 "아직 그 매장만 아는 상품" 이고,
여러 매장이 붙었으면 실재가 검증된 상품이다. 관리자 화면(§11)의 정렬 기준으로 쓴다.

**상품은 공용 자산이다.** 등록한 매장이 소유권을 갖지 않는다 — 다른 매장도 같은 상품에 자기 `shop_listings` 를 붙인다.
다만 **수정 권한은 등록 매장과 관리자에게만** 준다. 아무나 고치면 남의 판매 정보가 흔들린다.

### product_components — 이 상품 안에 무엇이 들었나

`productId`, `kind`(`game` / `dlc` / `soundtrack` / `artbook` / `figure` / `steelbook` / `code` / `goods`),
`gameId`(nullable), `label`, `qty`.

- 포켓몬 스칼렛, 바이올렛 세트: 상품 하나 + 구성품 두 줄(각각 다른 `gameId`)
- DLC 동봉판: 본편 한 줄 + DLC 한 줄. DLC 도 `games` 행이다
- 한정판: 본편 + 아트북 + 피규어 + 사운드트랙

게임 상세의 "파는 곳" 은 `product_components.gameId` 로 찾는다.
**세트에 끼어 있어도 그 게임 페이지에 뜬다.** 대표 `gameId` 하나로는 못 하는 일이다.

### shop_listings — 매장이 실제로 파는 것

`shopId`, `productId`, `condition`(`sealed` / `new` / `used`),
`priceMinor`, `discountMinor`, `currency`, `onHand`, `held`,
`status`(`draft` / `selling` / `soldout` / `hidden`),
`source`(`manual` / `csv` / `api` / `pos`), `externalId`, `stockUpdatedAt`, `isUnique`, `fulfillment`.

같은 상품이라도 신품과 중고는 **다른 행**이다. `available = onHand - held` 로 계산해 화면에 낸다(§12.1).

### shop_listing_units — 중고 한 점

`listingId`, `unitNo`, `grade`(`S` / `A` / `B` / `C`),
`hasBox`, `hasManual`, `hasInsert`, `hasCase`, `defectNote`, `soldAt`.

곽팩이냐 무곽이냐는 상품의 `packageType` 이 정하고, **그 물건에 실제로 박스가 남아 있냐**는 여기 `hasBox` 가 답한다.
둘은 다른 질문이다 — 곽팩으로 나온 물건인데 박스를 잃은 중고가 레트로에는 흔하다.

### shop_listing_photos

`listingId` 또는 `unitId`, `url`, `sortOrder`.
중고와 레트로는 실물 사진이 없으면 안 팔린다. Blob 한도가 있으니 장수 상한과 리사이즈 기준은 상수로 둔다.

## 5. 게임과 상품을 잇는 일 (매핑, 그리고 역방향 수집)

게임과 상품이 다른 테이블이니 **잇는 기능이 상시로 필요하다.** 세 방향이 있다.

### 5.1 등록 시점 매핑 (사람)

매장이 상품을 만들 때 제목으로 후보를 띄우고 **매장이 고른다.**
쓰는 자산은 이미 있다 — `title_en_norm`, `title_ko_norm` 생성 컬럼, `game_aliases`, trigram `similarity()`.

### 5.2 주기 매핑 배치 (기계)

`gameId` 가 빈 상품을 모아 카탈로그와 대조하는 크론. 매칭 파이프라인을 그대로 재사용한다.

- 유사도 높음: 자동으로 잇고 `created_source = 'cron:product-match'` 로 남긴다
- 중간: 관리자 검수 큐로
- 낮음: 그대로 둔다. 상품은 `gameId` 없이도 팔린다

### 5.3 역방향 — 매장이 등록한 게임을 수집 대상에 넣기

매장이 새로 만든 게임(§7)은 외부 ID 가 없다. 배치가 제목으로 스팀, PS, Xbox 를 검색해 후보를 찾고
검수 큐에 올린다. 붙으면 그 다음부터 가격과 메타를 크롤러가 채운다.

**단, 레트로는 이 배치를 타지 않는다.** 온라인 스토어에 없다. `games.crawlExcluded = true` 로 고정한다(§6).

## 6. 레트로, 그리고 크롤링 제외

### 기종을 `platformEnum` 에 넣지 않는다

현재 `platformEnum` 값은 전부 **우리가 크롤링하는 디지털 스토어**다.
여기에 슈퍼패미컴을 더하면 크롤러가 영원히 만들 수 없는 값이 크롤러 코드의 타입에 섞이고,
기종 하나 늘 때마다 마이그레이션이다.

### hardware_models — 기종 사전

`code`, `nameKo`, `nameEn`, `maker`, `generation`, `releaseYear`, `isRetro`, `mediaType`, `sortOrder`.

현행기도 같은 표에 넣고 디지털 `platformEnum` 값과는 코드 문자열로 맞춘다.
기종 추가가 관리자 화면의 행 하나가 된다. 배포가 필요 없다.
이 표는 사양 축(`docs/기획_사양_내PC호환성_2026-09-17.md`)과 **같은 표를 쓴다.**

### games 에 붙는 세 컬럼

- `origin` (`crawler` / `shop` / `admin`) — 이 행을 누가 만들었나
- `visibility` (`public` / `shop_only`) — 전체 목록과 검색에 나오나(§7)
- `crawlExcluded` (boolean) — 수집 대상에서 뺀다. 레트로와 굿즈가 여기 걸린다

`sync/` 의 대상 질의 **한 곳에서만** 이 조건을 본다. 여러 곳에 흩으면 한 곳이 빠지고
그 경로만 레트로를 긁으러 갔다가 매번 빈손으로 돌아온다.

### 레트로가 화면에서 다른 점

- **가격 비교가 비어 있다.** 온라인 스토어에 안 판다. 레트로 상세는 처음부터 **매장 시세**가 주인공이다
- 지역, 매체, 정품 여부, 구성품이 가격의 절반이다

## 7. 게임 등록 — 매장에 맡긴다

**매장이 직접 게임을 만든다. 승인 없다.** 대신 오염을 막는 장치를 컬럼과 화면에 둔다.

- 새 게임은 `origin = 'shop'`, `visibility = 'shop_only'` 로 생긴다
- `shop_only` 게임은 **매장 페이지와 그 상품에서만 보인다.** 전체 게임 목록, 검색, 홈에 안 나온다
- 매핑 배치(§5.2)가 기존 게임을 찾아내면 상품을 그 게임으로 옮기고 임시 행을 접는다
- 관리자가 확인했거나 크롤러 소스가 붙으면 `visibility = 'public'` 으로 승격
- 등록 폼은 **제출 직전에 한 번 더 검색을 강제한다.** 중복의 대부분은 검색을 안 해서 생긴다

관리자 검증이 0인데 카탈로그 오염도 0이다. 중복이 생겨도 매핑 배치가 천천히 접는다.

사람이 적은 값은 `data_corrections` 에 `lockField = true` 로 잠근다(AGENTS §7).

## 8. 재고 입력 — 손입력과 연동을 처음부터 같이

### shop_integrations — 연동 설정

`shopId`, `channelId`, `kind`(`csv` / `api` / `pos`),
`credentialRef`(비밀은 DB 에 넣지 않는다, 참조만), `isActive`, `lastSyncAt`, `lastStatus`.

### shop_sync_logs — 연동 실행 기록

`integrationId`, `startedAt`, `finishedAt`, `processed`, `failed`, `status`, `errorSample`.
기존 `sync_logs` 와 같은 모양으로 둔다. 관리자 화면도 같은 컴포넌트를 재사용한다.

### 규칙

- `shop_listings.source` 가 그 행을 마지막으로 정한 경로를 말한다
- **연동이 사람이 고친 값을 덮지 않는다.** 이미 배운 규칙이다(AGENTS §7 의 `lock_field`)
- 외부 값이 `null` 이면 기존 값을 덮지 않는다. 재고 수량만 예외다 — 0은 진짜 0이다
- 손입력 화면과 연동이 **같은 서비스 함수**를 통과한다. 갈리면 이력이 한쪽에만 남는다

## 9. 매장 직원 계정

### shop_staff

`shopId`, `userId`, `role`(`owner` / `manager` / `staff`), `invitedBy`, `joinedAt`.

이름을 `shop_members` 에서 바꾼 이유: "members" 는 고객 회원으로 읽힌다. **이 표는 직원이다.**

**1인 매장이면 필요 없지 않나** — 필요하다. 이유는 §2 의 감사 컬럼과 같다.

- 사장과 알바가 계정을 공유하면 `updated_by` 가 전부 같은 사람이고
  **"누가 재고를 0으로 내렸나" 에 영원히 답할 수 없다.** 감사 컬럼을 넣는 의미가 사라진다
- 알바가 그만두면 그 사람만 끊어야 한다. 계정 공유면 비밀번호를 매장 전체가 바꾼다
- 매장 하나에 사람 하나면 이 표에 행이 하나다. 복잡도는 행 하나 값이다

**가입은 하나로 유지한다.** 매장마다 로그인을 따로 만들지 않는다.
매장 소속은 가입 뒤에 붙는 관계다.

- 매장주: 일반 가입, 입점 신청, 관리자 승인, `shops(active)` + `shop_staff(owner)`
- 직원: 매장주가 초대(`shop_staff_invites`), 가입 또는 로그인, `shop_staff(staff)`

고객이 매장을 구독하는 개념(v1 의 `store_followers`)은 **1단계에서 뺀다.**
위시리스트와 알림이 이미 있으니 필요해지면 그 위에 얹는다.

## 10. 권한

- proxy 가 `/vendor/*` 를 `role in (seller, admin)` 으로 막는다
- 매장 단위 권한은 **서버 액션에서 다시 본다.** 설계서 §6 "middleware 만 믿지 않는다"
- **관리자는 모든 매장을 통제한다.** `requireShopRole()` 에서 admin 은 항상 통과하되,
  그 행위는 `updated_source = 'admin'` 으로 남는다.
  매장주가 나중에 "내가 안 했는데" 라고 할 때 답이 되는 것이 이 한 줄이다

```ts
// server/auth/guards.ts
requireShopRole(shopId, ...roles): Promise<ShopStaffRow | AdminOverride>
```

남의 `shopId` 를 폼에 박아 보내는 것이 이 도메인의 첫 공격이다. 액션마다 막는다.

## 11. 화면

### 공개, 유입

- `/business` — **입점 랜딩.** 왜 입점하나, 무엇이 되나, 수수료, 신청 버튼
- `/shops/join` — 입점 신청 폼. 사업자번호, 매장명, 주소, 연락처, 증빙 업로드
- `/shops/join/status` — 신청 상태. 심사 중, 반려 사유, 재신청
- `/shops` — 매장 찾기(거리순)
- `/shops/[slug]` — 매장 페이지
- 게임 상세의 "파는 곳" 섹션

### 매장주 `/vendor`

- `/vendor` 내가 속한 매장 목록. 하나면 바로 넘긴다
- `/vendor/[shopSlug]` 요약. 품절 임박, 오래된 재고, 조회수
- `/vendor/[shopSlug]/listings` 판매 목록. 재고 인라인 수정, 바코드 스캔 등록, CSV
- `/vendor/[shopSlug]/products/new` 상품 만들기. 게임 찾기, 없으면 새 게임 등록(§7)
- `/vendor/[shopSlug]/staff` 직원 초대, 권한
- `/vendor/[shopSlug]/integrations` 연동 설정과 실행 기록(§8)

### 관리자 — `/admin` 아래에서 뺀다

`/admin/shops` 는 주소를 잘못 치면 `/admin` 으로 들어간다. **`/shops/admin` 으로 옮긴다.**

그러면 `/shops/[slug]` 와 충돌한다. 매장 slug 가 `admin` 이면 관리 화면이 가려진다.
**예약 slug 목록**을 `lib/routes.ts` 에 상수로 두고 입점 신청에서 막는다(`admin`, `join`, `new`, `search`).

진짜 방어는 경로가 아니다. `requireRoleOrForbid("admin")` 이 없으면 경로를 어디로 옮겨도 뚫린다.
**경로 분리는 실수 방지고, 권한 검사는 보안이다.** 둘 다 한다.

- `/shops/admin` 입점 심사, 승인, 정지
- `/shops/admin/products` 상품 중복 정리, 매핑 검수.
  정렬 기준은 **판매 매장 수**다(§4.1) — 한 매장만 아는 상품이 정리 대상 후보다

## 12. B(예약), C(결제, 배송)가 붙을 자리

### 12.1 재고는 처음부터 `available = onHand - held`

A 에서 `held` 는 항상 0이다. 그래도 계산을 거쳐 화면에 낸다.
B 에서 예약 홀드가 들어올 때 화면과 서비스 코드가 한 줄도 안 바뀐다.

### 12.2 상태 전이는 함수 한 곳

`server/services/commerce/transitions.ts` 하나가 listing, 재고, 나중의 주문 상태를 바꾼다.
C 의 PG 웹훅도 같은 문으로 들어온다.

### 12.3 주문 구조 — fitin-app 에서 가져온 것

`fitin-app` 의 주문 API 를 읽고 온 결론이다(그쪽은 이미 겪은 구조다).

- **주문 하나에 결제가 여러 건이다.** 포인트 + 카드 분할이 흔하다.
  `order_payments` 는 1:N 이고 결제 유형(PG / POINT / MANUAL), 수단, 할부 개월을 각 행이 갖는다
- **할인도 여러 줄이다.** 쿠폰과 프로모션이 따로 붙는다. `order_discounts` 1:N
- **품목마다 진행 상태가 따로 있다.** 주문 상태 하나로는 부분 취소, 부분 배송을 못 적는다.
  우리는 한 주문에 신품과 중고가 섞이니 더 그렇다
- 금액은 원금액, 할인액, 최종액으로 층을 나눠 적는다. 단일 `price` 로 두지 않는다
- 주문번호는 PK 와 별도로 둔다. 사람이 부르고 CS 가 찾는 번호다
- 장바구니가 주문과 별도 테이블이다. 여러 매장 물건이 한 장바구니에 담기면 주문은 매장별로 쪼개진다

예상 이름: `orders`, `order_items`, `order_payments`, `order_discounts`, `order_shipments`,
`shop_settlements`, `carts`, `cart_items`.

### 12.4 `fulfillment` 컬럼을 A 부터

값은 `inquiry`(A), `pickup`(B), `delivery`(C) 로 는다.
나중에 컬럼을 만들면 기존 행의 과거가 불명이 된다.

### 12.5 이력은 A 부터

`shop_stock_events`(`beforeQty`, `afterQty`, `reason`)는 A 에서도 돈다.
나중에 켜면 그 전 기간이 통째로 공백이다.

### 12.6 재고 차감은 트랜잭션과 행 락

주문이 붙는 순간 여러 사람이 같은 행을 동시에 만진다.
주문 생성과 재고 감소는 한 트랜잭션이고 그 안에서 `select ... for update` 를 잡는다.
안 잡으면 재고 1개가 두 명에게 팔린다. Upstash 락은 여기 쓰지 않는다 — 그건 크론 중복 방지용이다.

### 12.7 안 하는 것

- 주문, 결제, 배송 테이블을 **미리 만들지 않는다.** 빈 테이블은 문서가 아니라 부채다
- 상품과 재고를 `game_platforms` 나 가격 스냅샷에 넣지 않는다. A 든 C 든 불변이다

## 13. 단계

1. **매장** — `shops`, `shop_staff`, `shop_staff_invites`,
   입점 랜딩과 신청, `/shops/admin` 심사. 감사 컬럼(§2) 소급을 여기서 같이 친다
2. **상품, 재고** — `hardware_models`, `products`, `product_components`, `shop_listings`,
   `shop_listing_units`, `shop_listing_photos`, `shop_stock_events`,
   `/vendor` 등록 화면, 게임 상세 "파는 곳", `/shops/[slug]`
3. **매핑, 등록** — 매장 발 게임 등록(§7), 매핑 배치(§5.2), 역방향 수집(§5.3)
4. **연동** — `shop_channels`, `shop_integrations`, CSV, 온라인 채널
5. **B, C** — 예약, 결제, 배송, 정산
6. **중고거래** — `shops.shopType = 'personal'` 개방, 개인 간 거래 규칙

감사 컬럼 소급을 1단계에 붙이는 이유: 나중에 하면 그 사이 쌓인 행이 전부 출처 불명이다.

## 14. 아직 안 정한 것

- 수수료와 정산 조건 (C 단계 전에 사업 결정이 필요하다)
- 개인 판매자(`shopType = personal`)의 본인확인 수준
- 바코드가 없는 레트로 물건의 상품 동일성 판정 기준. 구형 타이틀은 바코드가 아예 없다
- 매장 노출 범위 — 전국인가 지역 기반인가
- `platformEnum` 을 `storeEnum` 으로 개명할지(§1 딸린 제안)
